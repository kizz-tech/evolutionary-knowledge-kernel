# Задание агенту на реализацию EKK

## Вход и результат

Изучить текущий рабочий репозиторий пользователя, `architecture.ru.md`, `../spec/contract.md`
и реальные примеры. Если пользователь уже реализовал часть ядра, составить краткое
соответствие существующих компонентов целевой архитектуре и переиспользовать совместимое.
Эта спецификация не является основанием переписать работающий код целиком.

Результат первого прохода: локальный вертикальный срез, который читает realm,
позволяет предложить и безопасно применить изменение, выдаёт контекст по binding
и сохраняет проверяемое существенное наблюдение. Не нужен сервер, web UI или swarm.

Не создавать фиктивные классы, репозитории, агенты и файлы для всех будущих возможностей.
Не сообщать, что миграция выполнена, если выполнена только нормализация frontmatter.

## Этап 1. Формат и чистое чтение

Реализовать parser, IDs, resolver, schema/version handling, source pinning и снимок данных.
Сохранить неизвестные поля при round-trip. Отличать format validity от подтверждения
истинности, полномочий или продуктивности. Новые обязательные semantics требуют версии.

Критерии: чтение без LLM; стабильность ID при move; отсутствие duplicate IDs; обработка
битых локальных ссылок; явная непроверенность внешних ссылок; сохранение original source bytes;
ошибка при неизвестной обязательной возможности; проверка symlink и path traversal.

Текущий `tools/validate.py` можно переиспользовать как тестовую опору, но он не заменяет
version store, authority resolver и runtime. Не раздувать production API вокруг деталей утилиты.

## Этап 2. Writer и recovery

Реализовать propose/apply с ожидаемым снимком, idempotency key, lease/serialization writer,
подготовкой изменения вне опубликованного дерева, валидацией и атомарной сменой published ref.
Читатели привязаны к снимкам. Ручная рабочая папка не объявляется транзакционным хранилищем.

Реальные результаты тестирования должны включать: повтор одного запроса; два изменения
одной revision; два независимых изменения; авария до и после публикации; отказ источника;
попытка rollback после чужого изменения; изменение policy после подготовки предложения.

Внешние файловые изменения и незакоммиченные данные требуют восстановления реальных bytes,
а не только возврата Git HEAD. Нельзя писать в исходный LIFEOS до отдельного разрешённого этапа.

## Этап 3. Binding и context

Реализовать локальные профили и явное разрешение realm alias. По умолчанию нет глобального
сканирования всех папок пользователя. Конфликт/отсутствие binding не лечится whole-vault fallback.

В context выдаются обязательные ограничения выбранной области, актуальные принятые решения,
их основания, релевантная история, конфликты и неизвестности. Manifest включает exact snapshots,
policy/pack digests, источники и неполноту. Сначала достаточно lexical search и явных ссылок.

При нехватке бюджета обязательные ограничения не обрезаются молча. Не обещать полноту
в отношении никогда не зарегистрированных ограничений. Не запускать команды из source.

## Этап 4. Работа и значимое сохранение

Реализовать capture/proposal для нового источника, наблюдения и результата. Нулевая запись
после тривиальной задачи допустима. Commitment с последствиями принимается в рамках
делегированных прав и связывается с точными bytes. Автоматическое подтверждение допустимо
только для заранее разрешённого класса операций, не по голословному `accepted: true`.

Подключить один существующий проект без переноса его deploy и тестов внутрь EKK.
Показать реальную задачу, где сохранённое ограничение повлияло на действие, и задачу,
где обнаруженная неопределённость не была превращена в факт.

## Этап 5. Миграция

Использовать `migration.ru.md`. Начать с пилотного контекста в отдельной копии.
Проверить полноту ledger, происхождение и ключевые запросы. Переключить только доказанно
перенесённый контекст. Не публиковать ни один исходник LIFEOS автоматически.

## Этап 6. Пересмотр и исследование

Ввести выбранные triggers, явный бюджет внимания, success/removal criteria и связь ожиданий
с результатами. Replay и held-out evaluator должны оставаться вне изменяемой области эксперимента.
Отдельно сравнить новую модель с прежним и упрощённым scaffolding.

## Определение готовности

Готовность показывается отдельными результатами: формат, безопасная запись, восстановление,
ограничение доступа, семантическая полезность и эффект на реальной работе. Один зелёный
`doctor` не может заменять их все.

После каждого этапа выдать: реально работающие команды; какие файлы изменены;
проверки и результаты; оставшиеся ограничения; следующий минимальный незакрытый контракт.
Не генерировать отчёт о преимуществах, которых ещё никто не измерил.
