# Decisions

Planning decisions for EKK 1.0. They grant no execution, installation or
publication authority. A decision changes only by an explicit new entry.

| ID | Decision | Reason / rejected alternative | Revisit when |
| --- | --- | --- | --- |
| D-1.0-01 | The entry and observer advisor is a replaceable small model behind the existing semantic-advice port. The current choice is GLiNER2.5-Decide; Laya is no longer the active candidate. | The owner selected GLiNER2.5-Decide on observed quality and expects to change models over time. Binding the release to one model would make every swap a redesign. | A model is swapped; this is a new evaluated condition, not a new decision |
| D-1.0-02 | Every advisor runs in shadow before it changes selection, and is compared with lexical BM25 on the same real tasks and owner samples. | Comparing a model against the 0.8 scorer would credit it for fixing an avoidable baseline defect. Shadow keeps model errors visible and cheap. | A model meets the pre-registered gain and stop conditions |
| D-1.0-03 | Benefit is evidenced by the field-use study of ordinary work and owner-labelled samples, stratified by agent model and EKK version. Mechanism tests establish integrity only. | The owner asked for evaluation inside the real workflow. Synthetic competitions say little about this use, and one remembered session is anecdote. | A separately requested controlled study is frozen |
| D-1.0-04 | Retention is asynchronous by default; `--wait` is the explicit synchronous path. | Synchronous publication blocked agents for about a minute or longer and caused most write failures. The durable queue already guaranteed same-key recovery. | A host needs the published receipt in its critical path |
| D-1.0-05 | `--brief` and `--compact` are one agent view; the full projection remains the default output. | Two near-identical display modes confused agents and the lossless compact mode was too large to read. | A consumer needs a separate machine-readable projection |
| D-1.0-06 | The 0.9 experience package is an input to 1.0, not a separate release, unless the owner keeps it separate. | Capture and recall are central to the 1.0 outcome; a separate 0.9 would duplicate its evidence plan. | The owner selects a staged 0.9 delivery |
| D-1.0-07 | Codex and Claude Code are the primary hosts. Any other coding agent joins by registration (an environment marker in `callers.yaml`) and the host-neutral skill, not by host-specific runtime code. | The owner works mainly in these two hosts and wants EKK to serve any coding agent. Host-specific branches in the runtime would multiply with every new agent. | A third host becomes a daily tool |
| D-1.0-08 | Entry latency is reduced by caching only immutable facts: Git objects named by their IDs within a process, and per-commit record indexes derived from a complete validated load across processes. Heads, grants, acceptance and candidates are never cached by revision. | Profiles showed repeated Git reads and full reloads of past commits, not ranking, dominated entry. A cache of facts that cannot go stale keeps exact equivalence; caching mutable state would not. | A cache would need to hold state that a publication can change |
| D-1.0-09 | A write verifies only operations that no earlier pass verified; `ekk recover`, restore activation and a missing or foreign checkpoint audit every operation and every historical blob. | A full audit on every write made writing impractical: 497 s for one write on the larger store, and no publication there for eleven days. With the checkpoint a write takes about 11 s. Old-object corruption is found by explicit recovery and backup instead of the next write. | A corruption incident shows that explicit recovery runs too rarely |
| D-1.0-10 | Experience is captured from four host events (`SessionStart`, `UserPromptSubmit`, `Stop`, `SessionEnd`), identically in Claude Code and Codex. Subagent turns and compaction events are not captured. | Agents retained an outcome in 12% of sessions with changes (40 of 332 in September). A subagent's result reaches the parent's final report, and the spool is on disk, so compaction loses nothing. Fewer hooks mean less foreground cost. | A host adds an event that carries information these four lack |
| D-1.0-11 | Episode rule 2 (replaces rule 1 of the same day): a session's unpublished reports close into an episode at session end or after 20 minutes without activity, where a prompt without a report is activity for up to three hours. The episode is recorded as one unaccepted outcome only when the repository changed and the change is credited to the session; a substantial report (1,200 characters or more) without such a change is held for the owner's review; everything else leaves nothing. A correction never publishes anything by itself: the outcome carries only the count. | Rule 1 would have published partial work (cuts at two hours or eight reports while the agent was still working), credited another session's commits, and published unreviewed correction candidates verbatim (rule precision about 0.73). Holding substantial reports keeps a diagnosis that changed no file without publishing it unseen; the owner's verdicts on held and automatic results are the measurement of both thresholds. | Owner verdicts show that automatic outcomes are mostly not worth keeping, that held results are mostly kept, or that useful sessions are skipped |
| D-1.0-12 | An owner preference is an unaccepted `decision` record with a `preference` annotation and the owner's own words as its source; a later preference supersedes an earlier one exactly, which gives rules their history. Instruction files carry only the agent contract. Acceptance stays a separate act for the few rules that must always apply. This answers Q4. Provenance is labelled, not authenticated: `stated_by: owner` is set only on the owner's own paths (the review page, or `ekk observe prefer` in a terminal); inside an agent host the command records `agent_reported`, which neither reaches the session card nor ranks above other matches. | Preferences in instruction files grow without bound and have no history or area. As records they surface only when the task matches, show only their current version, and keep the owner's words apart from an agent's reading. Making every confirmed preference governing would put all of them into every entry. Every process of the OS user can write to the realm, so a label describes origin for cooperating agents and cannot pretend to be a boundary. | Preferences accumulate past what the session card and entry can carry |
| D-1.0-13 | Records imported from an earlier system (`migration` metadata or `adoption: not_adopted`) are archive: they never govern, and in entry their relevance is multiplied by a prior of 0.5 rather than placed in a strict tier after every current match. Owner-stated preferences are multiplied by 1.5. Both priors are applied in the entry, the ranker itself returns plain BM25, and entry records the plain order beside its own so that the owner's relevance sample judges both. No imported decision family is migrated into typed records. | The owner no longer works with the earlier system and does not want the design tied to it. Imports are 88% of the larger store; a strict tier would hide the best match whenever it is an imported document, and no measurement had seen the effect of the tier or of the boost. A prior is the weaker assumption and the comparison on the review page is the measurement. | The owner's relevance sample shows one order clearly better, or an archive family proves to be needed as decisions in force |
| D-1.0-14 | At session start in a bound project the host hook gives the agent the contract, the current owner preferences and the latest recorded results. Recall at a change of focus inside a session is deferred. | The card is recall at entry without any action by the agent, and it replaces instruction layers as the delivery of the contract. Injecting on every prompt costs latency and risks noise before any of this is measured. | Repeated corrections do not fall after the card is in use |
| D-1.0-15 | Task-term query weights are measured but not applied. | On 794 and 167 real entry tasks, weighting query terms by their rarity across tasks left known-item recall@8 per target at 0.275 and moved it from 0.222 to 0.213. The plain path is as good, so it stays. | Owner-labelled samples show framing words crowding out topic matches |
| D-1.0-16 | Delegated context handoff (component G) is deferred. | Since 0.8.3 a repeated entry costs at most about 3 s, and a subagent's result reaches the parent's report. A handoff mechanism exists in only one of the two primary hosts. | Field use shows subagent re-entry as a visible cost |
| D-1.0-17 | The advisor model runs only in batch, when the owner's review is prepared, never on the entry or hook path. | GLiNER2.5-Decide needs 10–25 s to load and about 4.4 GB of memory per process against 0.5 s of inference. Shadow labels are compared with owner verdicts; nothing is applied. In a first smoke run it labelled an unrelated candidate "supporting" at 0.56, which is exactly what the comparison has to expose. | A resident advisor process is justified by a measured gain |
| D-1.0-18 | A repository change is credited to a session only when the session was alone in the checkout, or when its report names a changed file or a new commit. Uncommitted files are compared by a size-and-time signature taken when the observer runs, not by the list of dirty paths. | Parallel sessions in one checkout are the owner's normal way of working; crediting by workspace alone attributed one session's commits to another and skipped the author. A path list cannot see a further edit to an already dirty file. | A session's own file events become available from the hosts |
| D-1.0-19 | The owner's review page is the one place where a held result, a correction candidate and an automatic outcome are judged, and it lists the top items of the entry order and of plain lexical order mixed, so that one marking judges both orders. | One page a week bounds the owner's effort; the same marks measure the correction rule, the episode rule and the ranking priors. | Marks show the page is too long or a section is never used |
| D-1.0-20 | The registered hook command cannot fail its host (`… 2>/dev/null \|\| true`); the hook itself exits 0 on every error and writes the contract to the host before it spools anything. Hooks are registered only after a runtime that knows `ekk observe` is active. | A runtime without the command exits 2 on every prompt, and Claude Code treats a failing `UserPromptSubmit` hook as a block. The contract is worth more than the capture. | A host offers a non-blocking hook mode |
| D-1.0-21 | Supersession preserves standing: an unaccepted record cannot take the place of an accepted one. Its link is shown as a claim on the accepted row, and it appears only through ordinary ranking. Governing records precede all optional reading, and a governing record left out by the byte budget is reported as a required gap. | Any writer could otherwise force a note into every entry as the "replacement" of an accepted decision, and a governing decision could be crowded out silently with `incomplete: false`. | A review workflow for accepted replacements exists |
