# EKK 0.9: observations and experience in ongoing work

Release ID: `EKK-R-0.9`. Target version: **0.9.0**, a planning designation;
installed/package versions are unchanged. See [status](status.md) for authority,
progress and delivery state. This is the authoritative release specification.

## Product outcome

While completing ordinary work, an agent can notice a useful incidental finding,
preserve its grounds without distracting the user, and recall it when a later
decision makes it relevant. The finding can be challenged, refined or retired
without losing the historical account. The result must work without a particular
small model and without mandatory reflection after every task.

The central gap is a connected acquisition-and-recall workflow. EKK 0.8 already
has work observation events, selected-episode improvement, exact references,
durable publication and bounded belief assessment. These do not themselves
discover incidental findings or surface them during subsequent activity.

Retain useful successes and opportunities as well as friction. A memory of only
failures can encourage unnecessary intervention. More retained text is not the
success criterion.

## Delivery target and lanes

The target is a complete local release in the owner's existing environment:
kernel/CLI, the private Gateway's declared supported operations and the enrolled
host integration. Prepare a reviewed English public artifact. Actual public
publication and creation of an external observer repository are separate actions.
Do not silently describe retrospective log import as live observation.

| Lane | Required result for this release | Conditional result |
| --- | --- | --- |
| Experience workflow | Capture, bounded candidate handling, grounded persistence, contextual recall, challenge/correction and outcome linkage | Broader sources/domains after their adapters and evidence exist |
| Host integration | At least one real supported capture path during ongoing work and recall at a meaningful change of focus; explicit coverage elsewhere | Additional client hooks after capability inspection |
| Small-model advice | Model-neutral contract, optional local Laya shadow adapter, usable evaluation/data specification and recorded bounded evaluation on permitted material | A trained checkpoint and any applied selection policy, only when the data/quality prerequisites are met |
| Delivery | Frozen installation, compatibility/recovery evidence, disable/rollback path and English release candidate | Public upload, external repository and model distribution |

The core delivery does not depend on a positive model experiment. A missing core
capture/recall path blocks its acceptance. Conditional model work remains visibly
pending, rejected or completed with evidence; it must not be represented as
delivered merely because the core shipped.

## User scenarios

**S1 — Incidental structural finding.** Adding a discount requires changing the
same condition in three places. Preserve the observed locations/version. Keep
"pricing responsibility may be fragmented" as an interpretation. When pricing
is later refactored, surface the evidence and remaining uncertainty without
automatically creating or executing a refactoring task.

**S2 — Repeated friction.** Several independent operations fail under a shared
condition. Link distinct episodes and alternatives. Retries of one failure and
later summaries of it do not become additional independent observations. Do not
claim a failure rate when the number of relevant opportunities is unknown.

**S3 — Useful success.** A small diagnostic distinguishes two explanations, or a
component handles a new case without a workaround. The useful conditions can be
recalled later; no general best practice is inferred solely from one success.

**S4 — Changed conditions.** A refactor removes the observed coupling. Historical
evidence remains readable, but the old warning is no longer presented as a
current applicable problem. A new contradiction does not erase the old bytes.

**S5 — Routine work.** A local text/style edit with sufficient context completes
with zero required EKK calls, zero new records and no user-facing observer output.

**S6 — Outside software.** An investigation discovers that several reports share
one original source. Preserve source dependence rather than counting agreement.
The common contract supports other domains; release claims stay within observed
adapter coverage. Do not infer psychological diagnoses from personal-task logs.

## Requirements and acceptance

Each criterion needs appropriate evidence from its owning component. Fixtures
verify mechanisms; an actual permitted work episode verifies live integration.
No artificial second task-solving agent or fixed number of user tasks is required.

| ID | Requirement / reviewable acceptance |
| --- | --- |
| O01 | Capture visible, permitted evidence during ongoing work through a documented host adapter; preserve event identity, source coverage and source version. Missing channels are explicit. A post-task replay alone cannot satisfy live capture. |
| O02 | The main agent can emit a short finding when noticed, and the adapter can propose candidates from available events without requiring that emission. Neither a compulsory end-of-task form nor capture of hidden reasoning is required. |
| O03 | Candidates have a bounded local lifetime/storage budget, stable deduplication keys and durable receipts. Replay/crash does not duplicate a logical finding. Overflow, expiry and unavailable processing are observable; rejected candidates do not create canonical rejection notes. |
| O04 | Durable experience separates the observed episode, interpretation, forecast and proposed intervention. It includes a contestable statement, owner/target, exact available grounds, acquisition mode and relevant time. Unknowns are representable. |
| O05 | Retention states why the finding might matter and when it could be recalled. These cues are data, not executable triggers or permissions. A single significant supported case may be retained; no universal minimum repeat count. |
| O06 | Related episodes can be linked or consolidated without destroying originals. Exact duplicates, same-episode retries and copied summaries do not increase the independent evidence count. Claims of frequency identify the window/denominator or state that they are unknown. |
| O07 | Existing owner routing, canonical writer, conditional revision checks and queue semantics are used. No automatic whole-transcript import, personal fallback for unbound work or cross-owner training pool. Permission is checked before model input, reads and publication. |
| O08 | Relevant experience is available at work entry/continuation and at a supported change of focus during work. Selection uses the current intention, object and applicability, with exact/object matching available independently of semantic models. |
| O09 | A recall card identifies the finding, why it is relevant now, grounds, uncertainty and applicable/stale status. Optional advice has a bounded budget, cannot displace governing restrictions and is not repeatedly delivered unchanged within one work context. |
| O10 | Similarity, model score, repeated retrieval and agent agreement do not establish truth. The main agent can inspect exact grounds, reject advice or continue without it. Review depth follows the consequence of the intended decision. |
| O11 | Challenge, correction, supersession, retirement and known applicability changes affect future recall while preserving history. Strong evidence dependencies are distinguished from topical links. A changed Git commit alone does not invalidate every memory. |
| O12 | An observation can lead to code, a check, a tool, research, an external task, a method candidate or no change. Reusable methods keep their existing evaluation/admission lifecycle. Observation retention never creates execution authority. |
| O13 | Capture admission performs bounded local work; model inference and consolidation are outside the foreground critical path. Observer failure cannot prevent ordinary work. Recall waits have explicit deadlines and preserve ordinary context on failure. |
| O14 | Local source/retention boundaries, disable controls, operational cleanup and recovery are documented. Purging retained source material is separate from retiring a finding; derived copies and unavailable evidence are handled honestly. |
| O15 | The optional Laya advisor receives bounded self-contained authorized input and a pinned model identity. Initial behavior is shadow-only: no hidden deletion, ranking changes, acceptance or action. Invalid, late or unavailable output preserves baseline behavior. |
| O16 | Evaluation uses an explicit rubric and permitted examples, checks missed findings as well as false positives, RU/EN behavior, truncation, option-order sensitivity, calibration and cost. Training/evaluation splits keep related episodes together and separate later/project-held-out work. No uncalibrated score is called a probability of correctness. |
| O17 | Ordinary-use evidence distinguishes available, noticed, retained, delivered, considered, used/rejected and helpful/unhelpful/unknown. Record only justified stages; delivery is not benefit and appropriate rejection is not automatically failure. No required diary. |
| O18 | Preserve `ekk.record/0.1` compatibility, existing observation-gap semantics, exact source bytes, mandatory-context behavior and recovery. Verify against frozen installed artifacts and declared supported clients. Technical and benefit claims remain separate. |
| O19 | Local delivery identifies exact versions/hashes, actual enabled coverage, defaults, known limits and disable/rollback receipts. No unreviewed development-tree export or private host data enters public artifacts. |

Acceptance evidence belongs with completed [tasks](tasks.md); [status](status.md)
summarizes coverage and explicitly identifies unmet criteria. Requirements are
not waived through a positive model score or a successful synthetic example.

## Scope boundaries

No universal mandatory memory lookup; no reflection on every small edit; no
replacement tracker or second canonical knowledge database. No automatic source
text promotion into instructions. No universal causal diagnosis, autonomous
refactoring, complete-world sensing, whole-machine surveillance, LIFEOS migration
or pooled private training. Do not require a graph database, RL or trained model
to make the experience workflow usable.

The initial release supports one proven host path and bounded common semantics.
An unsupported client is labeled as such. Gateway CRUD/read support alone is not
evidence that a remote chat client provides an observation stream.

## Completion and uncertainty

Core release completion requires O01–O19 within their stated scope, the declared
local delivery and reviewable public candidate. O16 permits a bounded evaluation
of the base advisor; improved weights are a conditional deliverable. Product
benefit can remain `not_observed` at installation and is assessed through ordinary
use afterwards. Scientific superiority or a benchmark win is not a release gate.

First resolve host event access, current integration points, affordable budgets,
source material rights and permitted inference/training resources. These are
tracked as concrete first tasks, not filled with invented measurements. See
[design](design.md), [owners](services.md), [decisions](decisions.md) and
[research basis](sources.md).
