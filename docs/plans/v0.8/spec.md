# EKK 0.8: continuous work and improvement through use

Status: approved and locally implemented on 2026-09-21. Delivery evidence and
configuration boundaries live in `implementation.md`; public publication remains
a separate authorized action.

The release connects proportionate context, discoverable work continuity,
practical methods, improvement from actual experience, authored sources and
recoverable operations. Ordinary local edits remain ordinary: no mandatory EKK
call, reflection, record or new skill when existing context is sufficient.

## Deliverables

1. A short, progressively disclosed entry alongside exact full context. Mandatory
   restrictions must remain visible or explicitly require further reading.
2. Incremental, permission-filtered text discovery with aliases and exact source
   fragments; a work item can be found without knowing its identifier.
3. Persistent work intent, results, open questions and continuation, represented
   by ordinary versioned records. A plan, its completion and later limitations
   remain distinguishable. External trackers own their task state.
4. Usable research/design, software and personal-work methods with applicable
   inputs, tools, intermediate outcomes and stopping conditions. Experience can
   improve or retire a component, tool, check or method without rewriting goals.
5. Owner-selected read-only authored sources, minimal local tasks, and explicit
   waiting/continuation through the existing host. A date in text is not a
   registered schedule. Unknown external outcomes are reconciled before retry.
6. Faster reads/writes, a durable publication outbox and honest local/published/
   discoverable receipts. Recovery preserves the logical key and current rights.

Keep `ekk.record/0.1`, stable source bytes, ownership, current authorization,
conditional writes and existing method admission boundaries. Do not migrate
LIFEOS, import complete transcripts, add a universal belief server, build another
chat, or infer permissions from source text. Shared work survives a participant
without copying their personal archive.

## Delivery sequence and owners

T0 preserves the current source/runtime baseline. T1 implements proportionate
entry; T2 discovery; T3 work continuity; T4 performance and durable operations;
T5 practical methods; T6 experience-driven improvement; T7 sources/tasks/waiting;
T8 the reviewed installed release and profile integration. T1/T2/T4 precede T3;
T5/T6/T7 compose the resulting contracts before T8.

EKK owns application contracts and adapters. The host integration owns shared
client instructions and enrolled-profile projections. Domain projects own their
code, design system and verification. Human authors own their original notes.

## Acceptance

Check actual mechanisms: current access, exact versions, source integrity,
snapshot-pinned pagination, non-destructive author access, interruption and
publication recovery, concurrent attempts, lost responses, installation and
rollback. Preserve relevant existing compatibility tests. The optional read
budget aims at roughly 1–2k tokens; restrictions are not silently truncated.
Performance targets on a stated real corpus are warm entry median <=3s, p95 <=8s
and small durable local enqueue <=2s; report actual results separately.

Product benefit is assessed through ordinary owner use, feedback and selected
real task logs, distinguishing retrieval, delivery, use and helpful outcomes.
No separate artificial agent competition or fixed number of user tasks gates
use. Technical tests do not establish model improvement or universal transfer.
Zero retained records and removal of an obsolete process are valid outcomes.

The release is complete only when the connected workflow is available, not when
isolated API examples pass. Public artifacts are prepared through the allowlisted
export with private data excluded; public publication needs explicit authority.
