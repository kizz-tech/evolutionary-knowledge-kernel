# Подключение рабочего проекта к текущему runtime

Пользователю достаточно назвать продукт и нужный результат. Агент устанавливает
владельца, использует существующий realm и создаёт подключение только в пределах
разрешённой задачи. Неизвестный владелец не заменяется личным realm по умолчанию.

Подключение хранится в `.ekk/workspace.yaml` продуктового репозитория. Это пример
структуры исходного формата; IDs должны быть взяты из реального разрешённого store:

```yaml
schema: ekk.workspace/0.1
workspace_id: urn:uuid:WORKSPACE_UUID
profile: organization
bindings:
  - realm_alias: organization
    realm_id: urn:uuid:REALM_UUID
    contexts:
      - urn:uuid:CONTEXT_UUID
packs: []
execution:
  checks: []
```

`workspace_id`, `bindings`, `realm_alias`, `realm_id` и `contexts` принадлежат
исходному формату. `profile` — поле текущего runtime для выбора локальной роли.
Aliases разрешаются локальной конфигурацией вне Git; binding не включает личный
путь, токены и корпоративную историю. Поля checks описывают подключение к штатной
проверке продукта; одно чтение binding или pack ничего не исполняет.

Агент проверяет, что realm ID совпадает с профилем, contexts существуют и разрешены,
а выбранная роль соответствует владельцу. Глобальный `enter --cwd` разрешает
единственный применимый portable binding. Несколько охватывающих деклараций
требуют явного разрешения, а не выбора ближайшей; независимый вложенный продукт
не должен автоматически наследовать подключение родителя. Неоднозначность,
несовпадение ID или `unbound` блокируют доступ к знаниям до исправления привязки.
Они не разрешают автоматически создать другой root или вернуться к личной базе.

После подключения агент читает контекст, выполняет ограниченную задачу штатными
инструментами продукта и сохраняет существенное свидетельство через безопасный
writer. Принятие решения, изменение кода, обновление знаний, выпуск и наблюдённый
результат остаются отдельными фактами. Инструкции по фактическому JSON-интерфейсу
находятся в [using.md](using.md).

`company-x-knowledge` остаётся неактивной пустой заготовкой до определения владельца,
прав доступа и допустимых источников. Локальная заготовка не является корпоративным
пилотом. Профили под одним OS user не обеспечивают физическую изоляцию: реальное
подключение компании требует границы доступа, соответствующей её правилам.

Обновление pack рассматривается отдельно от подключения: version и digest
закрепляют фактический артефакт, а публичный метод становится обязательным только
после местного принятия. Никакой onboarding не публикует данные, не разворачивает
продукт и не доказывает исследовательский эффект EKK.

## Активация нового владельца

1. Зафиксировать реального владельца, допустимую среду доступа и источники. До этого
   заготовка остаётся `awaiting_owner`; её `owner: null` не заменяется догадкой.
2. Выбрать отдельный доступный этому владельцу каталог вне личного realm. Агент
   инициализирует его через `ekk init --root /authorized/path --title 'Owner knowledge'`.
   В текущем trusted-local режиме principal — OS user; если правила компании требуют
   иной границы, сначала предоставляется соответствующая среда, а данные не загружаются.
3. В локальном профиле этого владельца зарегистрировать фактические ID и путь.
   Не копировать личный профиль целиком. Создать нужные context-записи через
   `propose/apply`, задав их purpose и допустимые источники.
4. В каждом разрешённом продуктовом репозитории выполнить
   `ekk init --workspace --cwd /path/to/product --profile ROLE --realm ALIAS --scope CONTEXT_ID`.
   Existing binding не перезаписывается автоматически; ID сверяется с published store.
5. Выполнить `ekk doctor --profile ROLE --realm ALIAS` и `ekk enter --cwd /path/to/product`.
   Проверить отказ доступа из неподходящей роли. Сделать полную резервную копию
   с Git refs и проверить восстановление в отдельном месте до массовой загрузки.
6. Сохранить небольшой разрешённый источник через `capture`, сверить точные bytes
   и прочитать его в нужном контексте. Более крупный перенос выполняется по отдельной
   карте происхождения; исходники сохраняются, принятие не наследуется.
7. После проверки переключить агентский вход продукта на этот binding. Прежний
   writer отключить явно; наблюдать первые реальные результаты. Обновление pack,
   принятие решения и передача данных другому владельцу остаются отдельными действиями.
