# Контракт миграции LIFEOS

Цель: перенести знания, источники и полезные инструменты в EKK, а не сохранить прежние
System/Work/Research механизмы в качестве обязательных слоёв новой архитектуры.

## До записи

Установить фактические пути, Git roots, dirty и untracked файлы. Проверить вложенные Git-корни,
внешние sources, ссылки, конфигурацию агентных профилей, автоматические writer и scheduled jobs.
Предшествующий ответ или read-only проекция не заменяют инвентаризацию машины.

Сделать независимый snapshot и восстановить его в отдельную директорию. Снимок Git HEAD
без uncommitted/untracked bytes недостаточен. Не удалять raw источники после extraction.

## Миграционный пакет

Располагается в частном destination realm:

```text
migrations/<id>/
  manifest.yaml
  mapping.jsonl
  validation.md
```

Тяжёлые резервные копии находятся в отдельном разрешённом backup storage. В Git попадают
только допустимые manifest и ссылки, не секреты, credentials или копия всех media.

Пример строки ledger, не утверждение о существующем файле:

```json
{"origin":{"root":"legacy-root-id","path":"example.md","id":"legacy:example","sha256":"<actual sha256>"},"action":"migrate","targets":["legacy:example"],"reason":"preserve identity and meaning","validation":"pending"}
```

Действия: migrate, retain_external, archive, restricted_exclusion, approved_delete, needs_review.
Ни один оригинал не исчезает из учёта. approved_delete требует отдельного подтверждения,
а не автоматического решения мигратора. Split/merge сохраняют mapping всех исходных IDs.

## Семантическая классификация

Личные высказывания владельца не превращаются в выводы агента. Источники не превращаются
в принятые решения. Старое `accepted` сохраняется как исторический факт прежней системы;
не каждый старый системный запрет автоматически становится новым правилом EKK.

Код, фактический deploy, внешние задачи и календарь остаются у своих владельцев.
Их Markdown-описание не является исполнением или внешней синхронизацией.

Из старых методов выбираются пригодные packs. Старые маршрутизаторы, компиляторы,
автопубликации и запреты не переносятся по принципу «это уже было». Полезный механизм
переводится на новый контракт только после проверки его назначения.

## Проверки

Структурные: сохранность ID, отсутствие коллизий, доступность локальных ссылок,
соответствие источников digest, покрытие ledger, отсутствие сырых приватных данных
в публичном target, отключение прежнего writer после cutover.

Семантические: существенные ограничения, основания решений, действующее/историческое,
дата действия/дата знания, предпочтение/вывод агента, разрешённая область, противоречие,
недоступный источник, связь с кодом и результатом. Подготовить репрезентативные вопросы
из фактического корпуса и проверить ответы по первичным материалам.

Операционные: реальная задача на migrated context, повтор операции, восстановление,
конкурентное изменение и явное отсутствие полной гарантии там, где она не проверена.

## Переключение и возврат

Один scope имеет один активный writer. Во время миграции области могут переключаться
последовательно; длительная двусторонняя запись старой и новой систем запрещена.
Старые entrypoints получают read-only redirect или отключаются, включая фоновые задания.

Если после cutover появилась новая работа, откат не означает уничтожить её старым backup.
Нужен обратный changeset или экспорт новых изменений. Старый snapshot используется для
восстановления с проверкой версий и дальнейшего согласования.

Итоговый отчёт отдельно обозначает: copied, structurally_validated, semantically_checked,
cut_over, legacy_read_only, restore_verified и retired. Они не сливаются в одно «готово».
